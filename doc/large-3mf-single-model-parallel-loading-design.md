# 大型 3MF 单模型加载优化方案（实测重构版）

## 1. 结论

原方案把“单个大 XML 并行解析”放在首要位置并不最优。本次对真实文件埋点后确认，首要问题是数据结构和共享资源生命周期：稠密空字符串占用大量内存，同一共享网格被重复计算凸包，所谓 rvalue 加载仍发生深拷贝，子模型合并也发生整棵对象复制。

建议采用以下顺序：

1. 先消除重复计算、伪移动、稠密属性和无界缓存。
2. 保持现有 Expat 严格解析路径，建立可重复的性能与正确性门禁。
3. 只有在第一阶段完成后，才评估受限队列或专用几何快速解析器；不要直接多线程调用同一个 Expat parser。

第一阶段已实现并用目标文件验证：导入阶段平均从 **22.005 s 降至 5.139 s（4.28 倍）**，程序记录的内存峰值平均从 **1,982 MiB 降至 395 MiB（下降 80.1%）**。

构建命令：

```powershell
cmake --build out\weiyusuo-release\build --target CrealityPrint_Slicer --parallel 8
```

每个版本预热后执行三轮，命令参数保持一致：

```powershell
out\weiyusuo-release\build\src\CrealityPrint.exe `
  --info `
  --debug=3 `
  --logfile=<log-path> `
  --outputdir=<output-dir> `
  E:\3mf\土拨鼠多色K2p_x16.3mf
```

计时口径：

- `import_ms`：`[3MF_PERF] stage=import_total`，从进入 `_load_model_from_file` 到模型导入完成。
- `wall_ms`：外层进程墙钟，包含启动、版本检查和退出清理。
- 内存：程序的 `Pagefile(peak)` 与外层每 100/250 ms 采样的 Private/Working Set。
- 退出码 `-24` 是预期结果：导入完成并写出 `import_total` 后，CLI 才因文件版本 6.0.0.3 高于当前 CLI 01.09.03.50 而拒绝继续。测试没有把 `--allow-newer-file` 后续准备阶段混入导入计时。

原始日志位于 `benchmarks/large_3mf/baseline/` 和 `benchmarks/large_3mf/optimized/`；汇总数据位于 `benchmarks/large_3mf/results.csv`。

## 5. 已实施优化

### 5.1 结构化性能日志

新增 `[3MF_PERF]` 日志，覆盖：

- 子模型 XML 解析、队列峰值和解析 CPU 时间。
- 子模型合并、根模型解析和总导入。
- 每个体的几何、网格统计、凸包、面标注耗时。
- 大网格 `fill_initial_stats` 的邻接、拓扑和总耗时。

### 5.2 稀疏三角形属性

将 support、seam、MMU、fuzzy skin、face property 从“每个三角形一个字符串”改成 `{triangle_id, value}` 稀疏记录。目标文件 4,820,116 个三角形只保存 41,467 条有效记录；仅在确实存在 `face_property` 时才构造稠密 `its.properties`。

同时补齐 `Geometry::swap/reset` 对 MMU、fuzzy skin 和 face property 的处理，避免恢复路径残留数据。

### 5.3 共享资源真正复用

- 共享体直接复用原 `TriangleMesh` 和凸包的 `shared_ptr`。
- 共享体不再进入会先计算凸包的构造路径。
- support、seam、MMU、fuzzy skin 标注随相同三角形索引复制，处理时间接近 0 ms。
- 共享体从约 0.2–0.8 s/体降至日志分辨率下的 0 ms。

### 5.4 真正移动网格并只计算一次凸包

原 `add_volume(TriangleMesh&&)` 实际绑定到 `ModelVolume(const TriangleMesh&)`，发生完整网格复制并先计算一次凸包；导入器随后又计算一次。现在网格直接 move 到共享指针，只保留一次凸包计算，并在返回前保持原 API 的“凸包已可用”语义。

### 5.5 去掉无界 XML 队列

原生产者/消费者实现把解压块复制为 `std::string` 放入无上限队列。在最大子模型上，生产者显著快于 Expat 消费者，所谓并行实际增加了约 270 MB 峰值。

现在 miniz 回调直接流式喂给 Expat，并正确设置最后一块 `isFinal=1`。最大子模型的墙钟解析略有增加，但内存大幅下降，整体导入仍明显更快。

### 5.6 节点转移合并与备份合并

- `std::map::merge` 代替对 `const value_type` 的伪 move，子模型合并平均从 317 ms 降到 1.3 ms。
- 导入期间新增多个体时不再反复序列化不断增长的对象，所有体完成后只触发一次备份；其他调用点仍保持默认即时备份行为。

## 8. 后续方案与优先级

### P0：合入前门禁

1. 用普通 3MF、带 seam/fuzzy/face_property 的 3MF、非 Creality/Bambu 3MF、损坏 XML 各补一个回归样本。
2. 验证导入后再导出，比较共享网格、凸包、标注、对象变换和 UUID。
3. 把性能日志降为可配置开关或 debug severity，避免普通用户日志中出现大量逐体记录。
4. 目标文件门禁：三轮平均导入不高于 5.5 s，内部峰值不高于 450 MiB，65 条体签名必须一致。

### P1：有界解压/解析流水线（可选）

如果需要恢复解压与 XML 解析重叠，只允许使用固定字节预算的有界队列，例如 8–16 MiB，并实现背压、取消、异常传播和 Expat `isFinal`。以当前 5.14 s 为基线，若收益不足 5%，不建议引入线程同步复杂度。

### P2：单个大模型快速解析（有门槛）

最大剩余热点是约 3.8 s 的大 XML 解析。建议先做专用几何 token scanner，而不是直接按字节并行 Expat：

1. 严格识别规范化的 `<vertices>` / `<triangles>` 区段和属性引号边界。
2. 第一遍统计并确定对象、顶点、三角形和稀疏属性偏移。
3. 预分配目标数组后按完整元素边界分块并行解析数值。
4. 遇到未知命名空间、实体、CDATA、非规范布局或校验失败时立即回退现有 Expat 路径。
5. 快速路径与 Expat 路径必须生成相同签名；模糊测试覆盖截断、超长属性、非法索引和 XML 实体。

只有当通用语料回归通过，且目标文件再获得至少 20% 端到端收益时，才值得合入 P2。当前结果已经证明：对这个文件，先修复数据布局和共享资源复用，比先做单 XML 并行化更有效、风险也更低。
