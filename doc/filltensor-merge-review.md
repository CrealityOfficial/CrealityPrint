## 尚未消除的风险

以下第 2～4 项在功能分支新增代码中即可确认，不能通过选择某一侧冲突代码来消除；本次未重写场填充算法或模型区域的数据结构。

1. **已补齐四个平台库；原生整包仍待验证。** 已接入用户提供的 [Jenkins #6](http://172.20.180.14:8081/job/CR_Close_library/6/artifact/artifacts/) 中 Windows x64、Linux x86_64、macOS arm64/x86_64 静态库。同步静态宏、移除原 DLL 和新增的 DLL 打包逻辑，并让依赖复制跟踪源文件变化；macOS 按目标架构选库。架构和复制校验通过，但本机未执行 macOS/Linux 原生构建。Windows ARM64、Linux ARM64 不在产物中，不能据此宣称支持。外部依赖包需要重新安装，避免残留的 Windows 同名导入库。来源、版本和哈希见 `deps/CR_CLOSED/CR_FILLTENSOR/README.md`。
2. **高：隐藏的零稀疏密度可能使场填充完全不生成。** UI 对 `ipField` 隐藏普通密度，并根据内部系数判断“有填充”；`Fill.cpp` 仍从 `sparse_infill_density` 取值，非实心表面在密度不大于零时直接跳过。旧预设从 0% 切换到场填充是重点复现场景，不能仅检查 UI 参数可见性。
3. **高：对象的多个区域共用首个场填充配置。** `PrintObject::infill()` 只取首个 `ipField` 区域的内部系数、表面系数和单元类型，生成一个对象级句柄。不同部件、修改器或高度范围中的场填充设置可能无法分别生效。
4. **高：场计算失败可能静默缺填充。** 张量计算失败只记录日志；句柄为空时 `FillField` 直接返回空路径。应在切片层明确报错，或设计并验证可见的回退策略后再发布。
5. **中：大模型耗时、取消与并发安全尚未验证。** 新增 OpenVDB 和闭源张量预计算；该预计算块没有显式取消检查。40000 点限制针对后续采样网格，不能据此认定 OpenVDB 全流程内存有相同上限。同一句柄被多层并发查询，头文件没有线程安全约定，需要库实现方确认并实测。
6. **中：旧客户端及云端参数兼容。** 本次保证新代码迁移旧名称；导出的 `intelligent_infill` 及新增 `field` 枚举是否被旧客户端、云端参数白名单和分析平台识别，尚未验证。不能将单向迁移视作新旧版本双向兼容。
7. **中：多线结果裁剪会改变既有路径。** 功能分支将多线输出再与外轮廓求交；普通单线连续路径修复已保留，但多线、侧向蜂窝/晶格的路径数量、总长度及轮廓附近挤出仍需对比。
