## 3. 用数据目录版本控制隔离

### 3.1 构建配置

建议新增独立配置，名称为拟议接口：

```cmake
set(CREALITYPRINT_DATA_VERSION "7.3")
```

生成同名 C++ 常量，并统一提供目录解析函数。数据版本是兼容性决策，不从 `CREALITYPRINT_VERSION_MINOR` 自动推导。

| 软件版本 | DATA_VERSION | 工作目录 | 行为 |
| --- | --- | --- | --- |
| 7.3.x | 7.3 | 7.3 | 首次自动迁移，否则直接使用 |
| 7.4.x | 7.3 | 7.3 | 共用目录，不触发跨目录迁移 |
| 7.4.x，需要隔离 | 7.4 | 7.4 | 按 7.4 迁移规则初始化 |
| 7.5.x | 7.4 | 7.4 | 继续使用 7.4 |

提升数据版本的条件：参数语义、持久化格式、系统预设结构等变化，使旧程序不能安全读取新版写入的数据，或产品明确要求隔离。普通兼容性新增和修复不必提升。

共用数据目录意味着旧版与新版可能交替使用同一份数据，发布前必须验证双向读写兼容性，不能只验证新版能读旧版。

### 3.2 统一路径规则

- Windows 示例：`%APPDATA%\Creality\Creality Print\7.3`。
- macOS、Linux 沿用现有平台根目录规则，仅替换数据版本部分。
- Alpha 使用 `7.3 Alpha`，默认只从相同渠道的来源迁移，不跨正式版/Alpha 导入。
- 日志、崩溃处理、预设、设备、缓存、锁文件共享同一目录解析接口。
- 明确保留显式 `--datadir` 的现有语义；显式指定目录时不自动从默认安装目录导入。实施前核对当前调用链，避免附加两次版本目录。
- 本次不改为共享账户目录，7.0 与 7.3 的登录文件独立，避免扩大任务范围。

### 3.3 迁移规则表

规则应随程序发布，不根据磁盘目录名自动推测任意版本均可迁移。

```text
目标数据版本 7.3：来源优先级 [7.0, 6.0]
```

将来确需独立 7.4 时再增加，例如：

```text
目标数据版本 7.4：来源优先级 [7.3, 7.0, 6.0]
```

每条边必须有受支持的数据格式范围、转换步骤、规则修订号和验收用例。不能只配置来源目录而不实现转换。

区分三个概念：数据目录版本决定位置；转换规则版本决定执行哪些转换；运行状态记录决定是否完成。软件版本作为诊断与兼容性判断信息保存，不替代上述三者。

## 4. 自动来源选择与目标识别

### 4.1 目标判定

先恢复未结束的迁移事务，再判断正常目标，禁止简单使用 `exists()` 或 `is_empty()`：

| 目标状态 | 行为 |
| --- | --- |
| 迁移或全新初始化已完成 | 使用目标；若后来损坏，进入配置恢复，不重新覆盖导入 |
| 无状态记录，但存在有效用户配置 | 视作已使用目录；校验后补登记，不自动覆盖 |
| 仅有明确列入清单的日志、缓存或运行锁 | 视作未初始化，允许迁移 |
| 存在未完成事务 | 根据事务记录恢复或重建临时产物 |
| 有未知文件或损坏的用户配置且无可识别事务 | 保留目标，记录冲突；不自动覆盖或清空 |

对于最后一种情况，自动尝试现有配置备份恢复；无法恢复时结束本次启动并写入独立诊断日志。不可通过标记为“新用户”掩盖已有数据。

### 4.2 来源有效性

按 7.0、6.0 顺序检查：

1. 路径是允许根目录内的真实目录，与目标不同，不通过符号链接或目录联接指向外部。
2. 主配置可读取，或其合法备份可恢复；恢复仅写入迁移副本。
3. 配置及用户目录结构受对应适配器支持；核对配置中的实际版本，防止读取更高版本产生的数据。
4. 单个用户预设损坏不使整个来源失效。

若 7.0 的核心格式不受支持或主配置及备份均不可用，记录原因后尝试 6.0。若来源因进程运行、临时锁定或权限错误暂时不可读取，视作暂不可用，不静默退回较旧数据。

来源缺失或全部被明确判定为不可迁移时，以 7.3 默认数据全新初始化，报告注明未导入的原因，旧目录原样保留。全新初始化也写入完成状态，后续启动不自动重新导入。

## 6. 预设与参数转换

### 6.1 统一转换管线

```text
6.0 ── 6.0 适配器 ──┐
                     ├── 统一迁移模型 ── 目标参数适配 ── 校验 ── 7.3
7.0 ── 7.0 适配器 ──┘
```

6.0 直接迁入 7.3。可以复用历史转换步骤，但不能要求安装、启动 7.0，不能创建或修改正式 `7.0/`。

转换模型至少包含账户归属、预设类型与身份、父预设、显式覆盖值、兼容关系、设备关联及同步元数据。它是迁移内部模型，不要求替换现有正式存储格式。

### 6.2 引用映射

- 优先使用经过验证的稳定标识；旧数据缺少标识时使用精确映射表。
- 禁止按相近名称自动匹配不同机型、喷嘴或挤出机配置。
- 转换 `inherits`、`compatible_printers`、默认工艺/耗材引用、当前选择、文件名及对应 `.info`。
- 按依赖顺序处理继承链，检测环和缺失父项；隔离失败父项时同步处理依赖项。
- 映射后名称冲突采用确定性重命名并同步修复所有引用，不覆盖另一个预设。
- 已有多挤出机名称转换应改造成明确字段范围、可重复执行的规则，避免无差别替换备注或 G-code 字符串。

### 6.3 保留用户修改

- 差异型预设：转换原有显式覆盖项，叠加到映射后的新版父预设。
- 全量预设：只有能证明旧父预设及其版本对应时，才根据旧基线计算用户差异。
- 不能从当前旧 `system/` 推断它一定是用户预设创建时的基线；无法证明时保留显式值，按规则转换并报告不确定性。
- 新增字段采用新版父预设或新版默认值。
- 改名、枚举、单位、单值/数组、挤出机维度、废弃字段都使用明确规则；未知参数保留在隔离原件及报告中，不静默宣称兼容。
- 自定义 G-code 保留内容；若引用已废弃的占位符，记录兼容问题，不能盲目文本替换。
- 参数和新版约束冲突时，按明确规则处理；无法安全转换则隔离该预设，不随机替换为相似机型。

6.0 偏好适配同样需要规则。例如当前复制流程将 `max_recent_count` 强制设为 30；新方案只对缺失字段或明确的旧默认值应用默认迁移，保留其他自定义值。无法区分用户主动选择与旧默认值时，将该判断作为产品规则记录。

## 7. 执行流程、事务与恢复

### 7.1 启动顺序

```text
解析数据版本与目标目录
  → 获取目标迁移锁，恢复未完成事务
  → 判断是否已初始化
  → 选择来源并获取一致的数据副本
  → 在同级 staging 目录初始化新版系统资源
  → 转换配置、预设、设备及账户状态
  → 离线校验完整加载及引用关系
  → 写入迁移报告与准备提交状态
  → 提交目标目录，写入完成状态
  → 正常 AppConfig / 预设加载
  → 登录校验及受控云端同步
```

启动早期日志写入父目录内独立的迁移诊断位置，避免目标目录被提前打开或占用。实施时需调整 `init_app_config()`、PresetUpdater、ProfileFamilyLoader 与网络初始化顺序，不能通过临时修改全局 `data_dir()` 来让正常服务读写 staging。

### 7.2 一致性与并发

- 目标迁移锁放在目标目录之外，供多个启动进程共用；普通实例锁不能直接替代迁移锁。
- 检查来源运行状态，使用已验证的旧版锁协议；单凭 `applock.data` 文件存在不能认定进程在运行。
- 来源仍在使用时进行有上限的自动等待；超时则记录可重试状态并结束启动，不切换到 6.0 或创建空白配置。
- 对复制清单做复制前后内容校验，变化则重试。文件哈希不能单独证明多文件事务一致性，必须结合来源不写入的保证。
- 若现有旧版进程检测不足，补充可靠的检测方案后才能启用自动迁移；不能假设新迁移锁会被旧程序遵守。

### 7.3 状态记录

建议父目录存放事务记录，目标目录保存最终初始化记录；文件名为拟议设计：

```text
Creality Print/
  6.0/
  7.0/
  7.3/                         # 提交成功的正式目录
    migration/manifest.json
    migration/report.json
    migration/quarantine/      # 失败原件，不在活动预设目录内
  .migration-7.3/
    transaction.json
    migration.log
  .7.3.staging-<transaction>/
```

状态建议：`PREPARING → COPYING → CONVERTING → VALIDATING → READY_TO_COMMIT → COMMITTED`，失败分为可重试和已隔离局部失败。

记录来源/目标数据版本、来源实际应用版本、渠道、目标构建、规则修订、事务 ID、文件摘要及统计。不记录登录凭证或设备密钥。

### 7.4 提交与崩溃恢复

- staging 与目标放在同一卷，校验通过后尽可能使用目录重命名提交。
- 目标若已存在，仅允许移动已确认属于本事务或白名单运行文件的目录；未知内容不覆盖。
- Windows 不假设可以原子替换非空目录。旧占位目标先改名保留，再提交 staging，每步写入可恢复记录。
- 目录重命名和状态写入不是一个事务，因此重启时结合事务 ID、目标 manifest 和文件完整性识别“已提交但未记账”，禁止重复导入。
- 完成状态只在持久化校验通过后写入；局部隔离允许以 `COMMITTED` 加警告统计完成。
- 失败重建 staging 时，仅清理已验证在迁移根目录内、由本事务创建的路径。
- 磁盘不足、权限不足、来源占用等基础设施失败不得标记为全新初始化成功；下次启动继续重试。

全程不增加迁移弹窗。致命失败时诊断保存在父目录或平台临时日志位置，结束本次启动；不能为了继续启动而让半成品或空白目录变为正式数据。

## 8. 云端同步与并存版本

迁移成功前，不允许旧同步队列上传，也不允许云端下载覆盖 staging。转换后的预设需携带可识别的迁移状态，首次同步先做身份、版本和冲突检查。

必须确认云端是否区分客户端参数格式/版本。若 6.0、7.0、7.3 使用同一预设记录，新版上传可能影响旧版；单纯隔离本地目录不能解决该问题。

发布要求：明确服务端版本隔离或客户端兼容策略。对服务端不能安全接受的已转换预设，应保留为本地可用并暂缓自动上传，不能伪造同步成功。具体 ID、时间戳和 dirty 状态的处理以现有同步协议为准，不在迁移器里随意重置。

账户失效不影响已迁移本地数据的保存；各账户数据仍按原归属隔离。原版本继续读写原目录，新版本不监视并持续同步旧目录。

## 9. 模块与代码改动建议

| 模块 | 职责 |
| --- | --- |
| 构建配置/生成头文件 | DATA_VERSION、渠道与迁移规则修订信息 |
| `DataDirectoryPolicy`（拟新增） | 平台路径、数据版本、来源优先级、显式目录策略 |
| `DataMigrationManager`（拟新增） | 检测、锁、事务、复制清单、提交、恢复及报告 |
| 来源适配器与转换规则 | 6.0/7.0 格式读取、预设映射、字段和参数转换 |
| 系统资源初始化接口 | 对显式目标路径安装指定版本资源，不依赖全局应用实例 |
| `utils.cpp`、`CrealityPrint.cpp` | 统一工作目录与崩溃日志解析 |
| `GUI_App.cpp` | 替换现有 6.0 整目录复制，调整启动顺序，整合名称迁移 |
| `AppConfig`、`PresetBundle` | 支持隔离目标的读取、转换和校验，返回完整错误而非只打日志 |
| 云端同步入口 | 迁移完成门控及首次同步兼容检查 |

尽量抽取现有能力，不重写整个预设加载器。需要显式路径参数的地方先做小范围重构，避免迁移时触发正常应用的保存、更新和网络副作用。

## 10. 验收标准

| 场景 | 预期 |
| --- | --- |
| 只有有效 7.0 | 自动迁入 7.3，无迁移界面 |
| 只有有效 6.0 | 直接迁入 7.3，不创建正式 7.0 |
| 两者都有 | 固定优先 7.0，不混合数据 |
| 7.0 核心数据无效、6.0 有效 | 记录原因后迁移 6.0 |
| 7.0 只有个别预设损坏 | 保留 7.0 来源，隔离坏项，迁入其余数据 |
| 来源暂时占用或无权限 | 有上限等待/重试，不静默降级来源 |
| 没有可迁移来源 | 完成 7.3 默认初始化，并记录结果 |
| 已有有效 7.3 | 不重复迁移，不覆盖任何已有用户修改 |
| 已用 7.3 后配置损坏 | 从目标备份恢复，不重新导入 7.0 覆盖 |
| 目标只有日志/锁 | 仍能正确识别首次初始化 |
| 未知目标文件 | 保留并报告冲突，不清空 |
| 转换任一阶段进程退出/断电 | 重启可恢复，不把半成品作为正式数据 |
| 两个实例同时首启 | 只有一个迁移执行者，无重复提交 |
| 磁盘不足/文件权限错误 | 原目录不变，无虚假完成状态 |
| 多账户、未登录、本地预设 | 全部保留，账户归属正确 |
| 父项改名/删除、继承链/环、名称冲突 | 引用正确或明确隔离，不静默丢失 |
| 自定义根预设、多挤出机、枚举和单位变化 | 转换结果符合规则，用户覆盖值可追踪 |
| 迁移后离线启动 | 可加载预设和正常使用，无联网依赖 |
| 迁移后首次云同步 | 不把旧预设覆盖回来，不错误上传或污染旧版 |
| 软件 7.4、DATA_VERSION=7.3 | 使用 7.3，不创建 7.4，不触发跨目录迁移 |
| 新 DATA_VERSION=7.4 | 仅使用已注册且验证的来源转换路径 |
| 正式版/Alpha、Windows/macOS/Linux | 路径和渠道正确，日志与数据归属一致 |

测试分层：规则单元测试（真实参数差异）、目录 fixture 集成测试、故障注入恢复测试、代表性模型的加载和切片冒烟验证。新版系统默认值允许改变切片结果，不应要求新旧 G-code 字节一致；重点验证用户覆盖值、机型能力、参数有效性及预期变化。

迁移前后对来源允许清单做内容摘要比对，确认迁移器未改写来源。报告中分别统计迁入、转换、隔离、跳过数量，文件数量不能替代有效预设数量。

## 11. 实施顺序与交付

1. 固化 6.0/7.0 真实样本、最终 7.3 系统参数包及差异清单，核对登录/云同步协议和用户数据字段。
2. 引入 DATA_VERSION 和统一目录解析，覆盖崩溃日志、渠道及显式目录场景。
3. 完成迁移框架、事务恢复、来源判定和显式目标路径的资源初始化。
4. 实现两条来源适配器及参数规则，整合已有名称迁移，补齐隔离报告。
5. 接入启动流程和云同步门控，执行两条路径及故障矩阵验收。

交付物包括：代码、来源/参数映射规则、回归 fixture、故障恢复测试、本地报告格式及发布检查记录。

当前尚需在实现阶段确认：最终 7.3 参数语义差异；旧版运行/写入状态检测能力；云端对多版本预设的隔离能力；`extra_config`、`sync_data` 及混色数据中真实用户内容的边界。这些事项不改变已确定的产品规则，但决定转换规则和首次同步的具体实现。
