## 2. 问题现象

- 用户每次启动切片软件后点击耗材映射，准备页面会出现明显卡顿。
- 卡顿持续一段时间后软件恢复。
- 同步按钮在处理期间缺少有效的动态反馈，看起来像程序无响应。
- 期望点击映射后界面保持可交互，并通过同步动画反馈当前状态。

## 5. 根因分析

### 5.1 配置准备工作占用主线程

- 原自动映射流程会在 UI 调用链中等待 `ProfileFamilyLoader::request_and_wait()`。
- 配置文件加载、JSON 解析和耗材配置匹配完成前，主线程无法继续处理绘制和输入消息。
- 首次启动或配置缓存未就绪时，这部分等待更明显。

### 5.2 按耗材逐项提交导致重复重计算

- 原流程逐个调用耗材颜色更新和预设选择逻辑。
- 每个耗材项都会产生颜色或下拉框事件，继而重复触发配置导出、`on_config_change()`、切片预检、场景刷新和冲刷体积重算。
- 本地调试日志中，4 个耗材槽位的一次映射出现了多轮切片预检/场景刷新以及 8 次冲刷体积处理；实际数值取决于耗材数量和颜色、预设是否发生变化。
- 单次计算并非主要瓶颈，重复执行整套后续更新才是卡顿被放大的主要原因。

### 5.3 动画依赖被阻塞的 UI 消息循环

- wxWidgets 定时器和绘制事件需要主线程持续处理消息。
- 当主线程等待配置加载或连续执行多轮配置应用时，即使按钮已切换到同步状态，也无法及时推进动画帧。
- 原控件同时缺少完整的忙碌帧管理和可靠的定时器对象绑定，因此用户看到的图标保持静止。

## 6. 修复策略

### 6.1 后台准备，主线程仅做最终提交

- 将设备耗材过滤、配置缓存等待和预设匹配放到独立工作线程。
- `ProfileFamilyLoader` 首次启动后复用共享加载结果，自动映射使用 `wait_until_loaded()`，避免每次点击强制重新加载全部配置。
- 工作线程完成后通过 `CallAfter` 返回 UI 线程，只执行必须在 UI 线程完成的控件和配置提交。

### 6.2 批量应用同步结果

- 静默设置每个耗材项的颜色和预设，不再逐项投递颜色、下拉框事件。
- 先在内存中完成所有冲刷体积矩阵行列更新，再统一执行一次配置导出和脏状态更新。
- 将 `on_config_change()`、切片结果失效、动态耗材列表更新和场景刷新合并为每批一次。
- 保留单个耗材手工修改路径的原有行为，批处理抑制参数仅用于自动映射流程。

### 6.3 增加可见且可终止的同步反馈

- `HoverBorderIcon` 使用 `ams_rfid_0` 至 `ams_rfid_7` 八帧资源。
- 通过绑定到定时器对象的 `wxEVT_TIMER` 每 `80 ms` 切换一帧。
- 同步期间禁止重复启动同一任务，并显示同步提示。
- 请求完成、失败、远端超时或工作超时时统一停止动画。

### 6.4 防止过期任务回写界面

- 为自动映射增加 generation、窗口生命周期 token 和目标设备校验。
- 用户切换设备、窗口销毁或旧请求超时后，后台结果不能覆盖当前界面。
- 设备侧脚本命令延后到 UI 消息循环派发，缩短点击事件本身的同步调用栈。

## 7. 代码改动摘要

- `FilamentPanel.cpp/.h`
  - 增加后台自动映射准备任务、完成回调和有效性校验。
  - 增加批量结果应用路径。
  - 支持静默设置耗材预设以及只刷新控件、不重复持久化的更新模式。
  - 记录 `profile_wait_ms`、`prepare_ms` 和 `apply_ms`，便于后续性能定位。
- `Plater.cpp/.hpp`
  - 增加同步任务状态、超时、generation 和生命周期管理。
  - 增加按钮忙碌动画的启动/结束控制。
  - 冲刷体积计算增加 `persist` 参数，使批处理中可以只更新内存，最后统一保存和调度。
- `HoverBorderIcon.cpp/.hpp`
  - 增加八帧忙碌动画、定时器驱动、DPI 重建和结束恢复逻辑。
- `PrinterMgrView.cpp`
  - 设备耗材更新脚本改为异步派发模式。
- `ProfileFamilyLoader.cpp/.hpp`
  - 复用启动阶段异步加载结果，增加线程安全的等待和耗材缓存读取接口。
  - 避免自动映射每次强制重新扫描并解析全部配置文件。

## 9. 性能观察点

日志关键字：

```text
Auto filament mapping timings: profile_wait_ms=..., prepare_ms=..., apply_ms=...
```

- `profile_wait_ms`：等待启动阶段配置缓存完成的时间。
- `prepare_ms`：后台过滤、读取缓存和匹配预设的总时间。
- `apply_ms`：UI 线程批量提交耗材配置和刷新界面的时间。
- 若仍出现卡顿，应优先比较 `apply_ms`，并检查是否还有未纳入批处理的切片或场景刷新调用。

## 10. 风险与回滚

- 风险等级：`中`。
- 批量路径改变了事件触发次数，需要重点验证依赖逐项颜色/预设事件的界面是否仍能正确更新。
- 最终控件更新和配置应用仍必须在 UI 线程执行，但已合并为一次；耗材数量很大时仍需关注 `apply_ms`。
- 配置缓存复用需要关注运行期间配置源发生变化时的刷新时机。
- 回滚时需整体恢复后台准备、批量提交、按钮任务状态和 `ProfileFamilyLoader` 缓存接口，避免只回滚其中一部分造成接口或生命周期不一致。

## 11. 后续建议

- 在不同性能等级的 Windows 设备上记录首次与二次同步的三段耗时。
- 增加自动化或可重复的 UI 测试，覆盖“单击一次只启动一个任务”和“切换设备丢弃旧结果”。
- 若 `apply_ms` 在大槽位数量下仍然偏高，可进一步提供一次性重算全部冲刷矩阵的批量接口。
