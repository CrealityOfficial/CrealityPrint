## 2. 问题现象

### 2.1 用户反馈现象

导入指定 3MF，完成切片后导出 G-code，界面弹出错误：

```text
Failed to rename the output G-code file from
...\.34724.1.gcode.tmp
to
...\.34724.1.gcode
error code permission denied
Is ...\.34724.1.gcode.tmp locked?
```

### 2.2 样例3MF配置

从 `Metadata/project_settings.config` 读取到：

```text
printer_model                   = Creality K2 Plus
nozzle_diameter                 = [0.4]
filament_settings_id 数量      = 6
filament_map_mode               = Manual
filament_map                    = [1]
filament_map_2                  = [0]
filament_volume_map             = [0]
support_filament_nozzle_mapping = 0
```

这组数据存在两个需要区分的问题：

1. K2 Plus 当前只有一个物理喷嘴，六个耗材是六个逻辑耗材/CFS 槽位，不是六个物理喷嘴。
2. 项目有六个逻辑耗材，但 `filament_map` 只有一个元素，项目保存态不是完整映射。

### 2.3 新建项目复现补充

除问题样例3MF外，新建项目也可以暴露同一数据缺口：

1. 启动软件并选择 K2 Plus。
2. 导入一个模型，初始使用耗材1。
3. 将模型复制成四个对象。
4. 给对象依次选择耗材1、2、3、4。
5. 打开耗材分组或进入切片。

若软件启动时已经恢复多个项目耗材，但 `filament_map` 仍停留在默认 `[1]`，界面会提示映射数量与项目耗材数量不一致。这说明 `[1]` 不只可能来自错误的过渡版3MF，还可能由新项目初始化入口漏同步造成；两者的输入兼容策略不同，但共享“项目映射必须完整”的数据不变量。

### 2.4 日志证据

同一个预览临时 G-code 路径出现了重复导出：

```text
14:14:03  开始导出 .34724.1.gcode
14:14:10  .tmp 重命名成功

14:14:30  再次开始导出同一个 .34724.1.gcode
14:14:36  .tmp -> .gcode 重命名失败，permission denied
```

对应日志行：

- `9237`：第一次导出开始。
- `9833`：第一次 `.tmp` 重命名成功。
- `9980`：第二次导出同一路径。
- `10579`～`10581`：第二次重命名和打开目标文件均失败。

因此，文件重命名失败是最终表现；更早的异常是已经完成的 G-code 结果被再次判定失效，程序对同一个预览文件进行了第二次导出。

### 2.5 实际结果

- 第一次 G-code 生成和重命名可以成功。
- 后续配置同步把已完成结果判定为失效。
- 后端再次生成同一个临时 G-code。
- Windows 无法替换仍处于占用状态的目标文件，最终报 `permission denied`。

### 2.6 期望结果

- 项目配置、`Print` 运行配置和导出配置使用同一种 `filament_map` 表示。
- 正常新版本3MF始终保存完整映射，不再生成短数组项目。
- 没有 `filament_map` 参数的正式旧版本3MF在配置比较前完成迁移。
- 单喷嘴、多喷嘴、正常新项目和正式旧项目进入同一条稳定的数据链路。

## 4. 根因分析

### 4.1 `filament_map` 的业务含义

`filament_map[i]` 表示第 `i` 个逻辑耗材所使用的物理喷嘴，值为从 `1` 开始的物理喷嘴编号。

假设：

- `N`：逻辑耗材数量。
- `M`：物理喷嘴数量。

完整映射应满足：

```text
filament_map.size() == N
1 <= filament_map[i] <= M
```

单喷嘴并不是“没有映射”，而是 `M=1` 的退化情况。因此 K2 Plus 六耗材的完整映射是：

```text
[1,1,1,1,1,1]
```

### 4.2 为什么项目里会出现 `[1]`

当前代码存在多个数据入口，但没有在所有入口建立相同的不变量。

#### 4.2.1 配置定义只能提供静态默认值

`src/libslic3r/PrintConfig.cpp` 中：

```cpp
def->set_default_value(new ConfigOptionInts{ 1 });
```

配置定义初始化时还不知道项目最终有几个逻辑耗材，因此 `{1}` 本质上是初始占位值，不代表项目只有一个耗材。

#### 4.2.2 新增和删除耗材入口能够生成完整数组

`PresetBundle::set_num_filaments()` 和 `PresetBundle::update_num_filaments()` 会执行：

```cpp
filament_map->values.resize(filament_count, 1);
```

因此，经过新增/删除耗材入口的六耗材项目会得到：

```text
[1,1,1,1,1,1]
```

但这只能覆盖用户显式增删耗材的入口，不能覆盖软件启动时从配置恢复多个耗材预设的入口。

#### 4.2.3 启动恢复耗材列表时没有同步映射长度

`PresetBundle::update_selections()` 和 `PresetBundle::load_selections()` 会恢复 `filament_presets` 与 `filament_colour`，但问题版本没有同时按 `filament_presets.size()` 调整三个映射数组。于是软件可能出现：

```text
filament_presets.size() = 6
filament_map             = [1]  // 仍是配置定义的占位值
```

这解释了不依赖旧3MF也能复现的新建项目场景：启动软件后导入一个模型，复制对象并给对象选择已有的耗材 1/2/3/4。对象赋值只修改模型的逻辑耗材编号，不负责创建项目耗材槽位，也不应借此修补项目映射；如果启动恢复阶段留下了 `[1]`，对象赋值后仍会暴露同一个错误状态。

BambuStudio 对照实现会在选择恢复阶段按 `filament_colors.size()` 初始化完整 `filament_map`，并在 `set_num_filaments()` 中随项目耗材数量调整长度。其对象耗材赋值同样只修改对象的 `extruder`。因此最合理的责任边界是：

- 映射数组长度跟随项目耗材列表，不跟随当前模型实际使用了几个耗材。
- 复制模型不改变映射长度。
- 给对象选择已有耗材不改变映射长度。
- 新增、删除或启动恢复项目耗材槽位时，统一同步映射长度。

#### 4.2.4 自动映射和手动确认会保存完整数组

`FilamentPanel::apply_automatic_filament_nozzle_mapping()` 以及手动分组确认流程，会把最终映射完整写入 `project_config`。

因此，经过正常自动映射或手动确认的项目也会保存完整数组。

#### 4.2.5 3MF导入直接恢复原始项目值

`PresetBundle::load_config()` 在恢复耗材预设后执行：

```cpp
project_config.apply_only(config, s_project_options);
```

该步骤会把3MF中的 `[1]` 原样覆盖回项目配置，但随后没有按照已经恢复的六个耗材再次规格化映射长度。

最终形成两类表示：

| 项目来源 | 保存结果 |
|---|---|
| 启动恢复未同步、默认占位值、测试/过渡文件 | `[1]` |
| 新增耗材、自动映射、手动分组确认 | `[1,1,1,1,1,1]` |

二者业务含义可能完全相同，但原始数组比较结果不同。

### 4.3 样例项目的 Manual 状态边界

已确认以下事实：

- K2 Plus 的配置默认模式是 `AutoForSaving`。
- 导入产生的 `_temp_1.config` 已经是 `Manual + [1]`。
- 当前提供的源3MF本身也是 `Manual + [1]`。
- 因此，本次导入过程没有把 Auto 改成 Manual。

该文件来自测试/过渡版本，属于已经写入映射字段但内容不完整的错误3MF。本方案保留它作为本次问题的分析证据，但不把它列入正式兼容范围，也不为 `Manual + [1]` 增加专用迁移分支。`AutoForSaving` 按当前产品要求直接放开。

### 4.4 重复导出的代码链路

问题链路如下：

```text
源3MF：6个逻辑耗材，Manual，filament_map=[1]
  ↓
PresetBundle::load_config()
  ↓ 原样恢复项目配置
project_config：filament_map=[1]
  ↓
Print::process()
  ↓
Print::resolve_filament_mapping()
  ↓ 按6个逻辑耗材补齐
Print运行态：filament_map=[1,1,1,1,1,1]
  ↓
导出前再次调用 Print::apply()
  ↓
项目[1] != 运行态[1,1,1,1,1,1]
  ↓
filament_map 被判断为变化，切片/G-code结果失效
  ↓
同一个预览G-code被再次导出
  ↓
目标文件仍被占用，Windows重命名失败
```

### 4.5 根本原因

根本原因不是 K2 Plus 有六个耗材，也不是 Windows 重命名接口本身，而是：

1. `filament_map` 同时允许短数组和完整数组表示相同业务含义。
2. 项目层、`Print` 层和导出层没有在比较前使用同一套规格化规则。
3. 后端在配置比较基线建立之后才改变映射长度。
4. `filament_map` 会影响物理喷嘴参数和切片缓存，原始数组不相等会触发真实的结果失效。
5. `filament_map_2`、`filament_volume_map` 等派生字段进一步扩大了不同步概率。

## 5. 修复方案

### 5.1 方案比较

#### 方案A：单喷嘴绕过 `filament_map`

处理方式：只有 `nozzle_diameter.size() > 1` 时才解析真实映射；单喷嘴后端固定使用 P1。

优点：

- 能快速阻断 K2 Plus 的 `[1]` 与完整数组差异。
- 单喷嘴业务语义直观。

缺点：

- 所有下游消费者都必须正确区分单喷嘴和多喷嘴。
- 现有擦料塔、G-code、速度/层高参数索引中存在直接访问映射数组的路径，容易遗漏。
- 切换机型时需要在“无映射”和“有映射”两套状态之间迁移。
- 长期维护会持续增加条件分支。

该方案适合作为局部止血方案，不作为最终推荐架构。

#### 方案B：全局统一使用完整 `filament_map`

处理方式：把单喷嘴视为 `M=1` 的映射场景，所有项目始终保存与逻辑耗材数量一致的完整映射。

优点：

- 单喷嘴和多喷嘴使用同一数据模型。
- 下游可直接按逻辑耗材索引，不需要额外机型分支。
- 机型切换、3MF保存、G-code头信息和发送数据的语义一致。
- 可以从根本上消除 `[1]` 与完整数组的配置比较差异。

缺点：

- 必须增加旧项目迁移。
- 必须确保所有入口都执行同一个规格化函数。

综合现有代码结构、兼容成本和后续扩展，推荐方案B。

### 5.2 最终数据不变量

项目配置进入正常运行态后必须满足：

```text
N = 权威逻辑耗材数量
M = nozzle_diameter.size()

filament_map.size()        == N
filament_map_2.size()      == N
filament_volume_map.size() == N
1 <= filament_map[i] <= M
filament_map_2[i] == filament_map[i] - 1
```

其中：

- UI/项目层的 `N` 取 `filament_presets.size()` 或与其一致的耗材槽位数量。
- 后端完整配置中的 `N` 取 `filament_settings_id`/`filament_diameter` 的权威数量。
- 禁止把 `filament_map.size()` 本身作为逻辑耗材数量来源，否则旧的错误长度会反向影响规格化结果。
- `M` 取实际物理喷嘴数量，不使用 `support_filament_nozzle_mapping` 判断。
- `support_filament_nozzle_mapping` 只控制分组 UI 是否显示。

### 5.3 实际实现的统一校验与迁移入口

本次没有增加单一大而全的规格化函数，也没有让后端继续静默补齐短数组，而是把“迁移”和“校验”分开：

- `validate_complete_filament_map()`：统一检查映射长度是否等于逻辑耗材数量，以及每个物理喷嘴编号是否在 `[1,M]` 内。
- `build_legacy_filament_map()`：只用于正式旧项目迁移；单喷嘴生成全 `1`，多喷嘴按 `1..M` 循环生成完整初始映射。
- `prepare_project_filament_mapping_after_load()`：在项目 JSON 仍保留字段存在性时区分旧格式、完整新格式和错误中间格式。
- `validate_project_filament_mapping()`：保存项目配置前执行相同的完整性检查，阻止新版本写出短映射。

处理原则：

1. 正式旧格式只有在 `filament_map` 和 `filament_map_mode` 都不存在时迁移。
2. 当前格式必须带有完整、合法的 `filament_map`，不允许用默认值补齐。
3. `filament_map` 与模式字段仅存在一个，或数组长度/取值非法时，直接报告配置无效。
4. 迁移或合法性确认后，重新生成 `filament_map_2`，并把 `filament_volume_map` 调整到 `N` 项。
5. Manual 模式在切片层严格要求完整映射；Auto 模式可防御性地接收尚未同步的瞬时占位值，计算完整映射并由调用方在切片或保存前写回项目配置。
6. 切片层不再根据短数组反推逻辑耗材数量。

### 5.4 新项目和当前格式项目

#### 5.4.1 单喷嘴

例如 K2 Plus 六耗材：

```text
filament_map_mode   = AutoForSaving
filament_map        = [1,1,1,1,1,1]
filament_map_2      = [0,0,0,0,0,0]
filament_volume_map = [0,0,0,0,0,0]
```

单喷嘴可以隐藏分组 UI，但底层仍保留完整映射。

#### 5.4.2 多喷嘴自动模式

- 切片前根据当前 Plate 实际使用耗材、耗材兼容性和可用物理喷嘴计算完整映射。
- 计算成功后先写入项目配置，再把同一份完整配置传给 `Print::apply()`。
- 项目状态、切片状态和导出状态必须使用相同数组。

#### 5.4.3 多喷嘴手动模式

- 保留用户已经选择的合法映射。
- 正常新版本保存时必须包含全部 `N` 个逻辑耗材的映射。
- 已使用耗材映射到不存在或不兼容喷嘴时必须提示，不能静默更换。

### 5.5 旧3MF兼容

兼容范围只包含正式旧格式和正常新格式：

| 类型 | 原始数据 | 处理方式 |
|---|---|---|
| 旧格式 | 不存在 `filament_map` 和模式字段 | 按旧版本语义迁移 |
| 完整新格式 | 长度等于 `N` 且值合法 | 直接使用 |
| 错误中间格式 | 字段已经存在，但长度小于 `N` 或内容非法 | 不做兼容迁移，不纳入验收范围 |

#### 5.5.1 单喷嘴旧项目

对于完全不存在映射字段的单喷嘴旧项目，统一迁移为：

```text
filament_map_mode = AutoForSaving
filament_map      = N 个 1
```

这不会改变旧项目的物理打印行为。

#### 5.5.2 多喷嘴旧项目

正式旧项目没有显式手动分组意图，因此迁移后的模式统一使用 `AutoForSaving`：

- `N <= M` 时生成 `[1,2,...,N]`，与旧版按工具编号使用喷嘴的常规关系一致。
- `N > M` 时按 `1..M` 循环生成完整合法映射，后续自动模式会根据当前实际使用耗材和兼容喷嘴重新计算。
- 单喷嘴是该规则的特殊情况，无论 `N` 为多少都生成全 P1。
- 迁移只发生在内存中；用户主动保存时才写入当前完整格式。

#### 5.5.3 当前样例 `[1]` 的兼容边界

当前样例已经包含映射字段，因此不是“没有 `filament_map` 参数”的正式旧格式，而是测试/过渡版本产生的错误中间格式：

```text
Manual + [1]
```

最终方案不为这种文件设计自动修复、模式推断或专用兼容逻辑。测试时应使用当前正常版本重新创建并保存六耗材3MF，正常文件必须直接包含完整的六项映射。该样例只用于说明短映射与运行态完整映射为什么会造成重复导出，不作为修复后的兼容验收文件。

### 5.6 旧格式识别方式

本次不增加 `filament_map_version`。原因是 3MF 导入时的 `DynamicPrintConfig` 初始为空，`bbs_3mf.cpp` 在读取 `Metadata/project_settings.config` 后、叠加 `FullPrintConfig::defaults()` 前，仍可准确调用 `config.has()` 判断原文件是否包含映射字段。

因此，旧格式识别直接使用原始字段存在性：

```text
无 filament_map 且无 filament_map_mode  -> 正式旧格式，执行迁移
两者都存在且 filament_map 完整         -> 正常新格式，直接使用
仅存在其中一个或 filament_map 非法      -> 错误中间格式，拒绝加载
```

这样避免新增版本字段，也不会被默认 `{1}` 混淆。

### 5.7 规格化时机

本次实际覆盖以下关键入口：

1. 3MF 原始项目配置读取完成后：迁移正式旧格式，校验当前格式。
2. 普通 3MF 项目配置保存前：校验模式字段和完整主映射。
3. CxCloud G-code 3MF 项目配置保存前：执行同一校验。
4. 软件启动或切换预设恢复项目耗材列表后：按 `filament_presets.size()` 同步三个映射数组。
5. 新增、删除项目耗材槽位后：调用同一个同步入口维护数组长度。
6. `Print::resolve_filament_mapping()`：Manual 模式要求完整映射；Auto 模式允许瞬时占位值并计算完整结果，调用方随后写回项目配置。
7. Auto/Manual 确认流程继续沿用现有逻辑写入完整映射。
8. `AutoForSaving` 在映射模式菜单中恢复可见。

### 5.8 配置同步顺序

实际顺序：

```text
3MF/默认值/UI操作
  ↓
旧格式迁移或当前格式严格校验
  ↓
project_config 完整映射
  ↓
生成 full_config
  ↓
Print::apply() 比较完整映射
  ↓
m_config / m_full_print_config 使用同一份数据
  ↓
切片与G-code导出
```

`Print::resolve_filament_mapping()` 不再把 `filament_map.size()` 当作耗材数量来源。Manual 模式不补齐错误数组；Auto 模式保留一次防御性规格化能力，以便在 UI 项目状态尚未同步时仍可算出完整映射，但完整结果必须由调用方在进入切片或保存前写回。正常新项目由 `PresetBundle` 主动维持完整表示，正式旧项目则在3MF加载阶段完成迁移。

### 5.9 派生字段处理

本次以 `filament_map` 和 `filament_map_mode` 作为项目真值。3MF 加载成功后：

- `filament_map_2` 始终由完整主映射重新生成。
- `filament_volume_map` 调整到 `N` 项，已有项保留，缺少项补 `0`。
- 新项目在启动恢复、耗材数量变更及 Auto/Manual 确认时同步写入三个数组。

### 5.10 自动模式 UI

- `AutoForSaving` 按当前产品要求直接显示并正常参与模式选择。
- 单喷嘴机型可以不显示分组入口，但底层仍保存完整全 P1 映射。
- `support_filament_nozzle_mapping` 只决定 UI 可见性，不决定是否维护映射数据。
- Auto 放开后，正常新版本项目在切片和保存前写入完整映射；正式旧项目则通过“字段缺失”迁移进入完整格式。

## 7. 风险与回退

### 7.1 可能风险

1. 旧多喷嘴项目没有显式映射，循环初始映射及后续 Auto 计算可能与用户心中的隐含分组不同。
2. 规格化时错误选择逻辑耗材数量来源，可能导致新项目或旧项目迁移后的映射长度错误。
3. 旧项目迁移发生在配置比较之后，仍会造成多余重切片。
4. 有效映射变化未触发对象切片失效，则可能继续使用旧喷嘴层高/速度参数。
5. `filament_map_2` 和 `filament_volume_map` 未同步，会在发送、预览或G-code解析阶段出现不一致。
6. 加载旧项目时立即标记项目脏，可能影响用户关闭项目体验。
7. 机型切换时保留超出新喷嘴数量的旧映射，会产生非法物理喷嘴编号。

### 7.2 风险控制

- 在默认值注入前按原始字段存在性区分正式旧格式和当前格式。
- 单喷嘴迁移不改变物理行为。
- 多喷嘴旧项目生成确定性的循环初始映射，并交给默认 Auto 模式按当前条件计算。
- 当前格式字段存在但非法时直接失败，不静默猜测或修补。
- 将规格化放在 diff 之前，并区分表示变化与语义变化。
- 规格化后的配置作为当前加载基线，避免仅因兼容迁移立即显示项目已修改。
- 主映射和派生字段原子更新。

### 7.3 风险影响范围

- 所有 FFF 项目的3MF加载和保存。
- 单喷嘴多耗材项目。
- 多喷嘴自动/手动分组项目。
- 打印机和喷嘴数量切换。
- 依赖物理喷嘴索引的切片、擦料塔、G-code和发送数据。

### 7.4 回退方案

- 若统一映射修改引入严重回归，应整体回退 3MF 加载迁移、保存校验和严格解析逻辑。
- 不建议只回退项目加载或只回退 `Print::apply()`，否则会重新形成项目层与运行层不一致。
- Auto 模式放开属于已确认产品要求，不随本次映射规格化方案回退。
- 回退后旧3MF仍应保留原始字段，不得在失败迁移时覆盖源文件。
