## 2. 问题现象
- F022 设备执行发送打印前的文件校验时，使用个人预设或项目预设会提示“切片机型与打印机不匹配”。
- 即使预设对应的实际打印机型号与当前 F022 设备一致，仍会触发机型不一致风险弹窗。
- 该误报会增加用户判断成本，并可能导致用户取消正常打印任务。

## 3. 影响范围
- 功能模块：`发送到打印机 / 文件校验 / 机型匹配`
- 影响设备：当前文件校验策略覆盖的 `F022` 设备。
- 影响预设：无法通过系统打印机预设名称直接查找到的个人预设和项目预设。
- 涉及仓库与文件：
  - C3DSlicer：`src/slic3r/GUI/print_manage/Routes/DeviceMgrRoutes.cpp`
  - CrealityCommunity：`SendToPrinterPage/src/cppManager.js`
  - CrealityCommunity：`SendToPrinterPage/src/views/composables/usePrintDevice.js`

## 4. 修复前复现步骤
1. 在 Creality Print 中选择或创建适用于 F022 的个人预设或项目预设。
2. 完成切片并进入发送打印页面。
3. 选择实际型号与切片机型一致的 F022 设备。
4. 点击开始打印，触发文件校验。
5. 观察到系统弹出“切片机型与打印机不匹配”的风险提示。

## 5. 根因分析
- 前端原先调用 `get_model_match` 时只传递两个预设名称：切片预设名称和设备预设名称。
- C++ 侧通过预设名称在系统打印机预设集合中执行 `find_preset`。
- 个人预设或项目预设的名称可能无法在该集合中直接命中，即使它们实际对应的 `printer_model` 与当前设备一致。
- 修复前只要任一预设查找失败，就直接返回 `match_result = 1`，因此产生机型不匹配误报。
- 问题本质是使用“预设名称是否可查到”替代了“实际打印机型号是否一致”的判断。

## 6. 修复方案
- 保留原有预设名称匹配路径，系统预设能够成功查找时继续使用现有 `printer_model` 与 `gcode_flavor` 规则，不改变既有结果语义。
- 前端在请求机型匹配时额外传递：
  - `printerModelA`：切片文件记录的实际打印机型号，即 `store.printerModel`。
  - `printerModelB`：当前设备在 `modelMap` 中对应的实际打印机型号。
- 当 C++ 侧任一预设无法按名称找到时，不再直接判定不匹配，而是使用实际打印机型号作为 fallback 进行比较。
- fallback 型号比较前执行统一标准化：
  - 去除首尾空白。
  - 已以 `Creality` 或 `SPARKX` 开头的型号保持不变。
  - 其他非空型号补充 `Creality ` 前缀。
  - 最终使用忽略大小写的方式比较。
- 任一 fallback 型号为空时按不匹配处理，避免缺少有效型号信息时被误判为匹配。

## 10. 风险与回滚
- 风险等级：`低`
- 风险说明：
  - fallback 仅在任一预设无法按名称查找到时生效，不影响两个系统预设均成功查找的原有判断路径。
  - 型号标准化依赖当前 `Creality`、`SPARKX` 品牌命名规则；新增品牌时需同步评估前缀规则。
  - fallback 信息缺失时仍返回不匹配，行为偏保守，不会放过未知机型组合。
- 回滚方式：
  - 回退 `usePrintDevice.js` 中新增的实际型号参数。
  - 回退 `cppManager.js` 中 `getModelMatch` 的参数和消息字段扩展。
  - 回退 `DeviceMgrRoutes.cpp` 中 fallback 型号比较逻辑，恢复预设查找失败时直接返回 `1`。
