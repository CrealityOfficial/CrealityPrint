# 崩溃系统 Top10：最小冲刷量耗材排序矩阵越界崩溃

## 1. 基本信息

- Bug ID：无（崩溃系统 Top10 自动采集）

- 反馈人：崩溃收集系统
- 处理人：
- 影响版本：Creality Print 7.2.1.5476
- 影响模块/影响文件：切片与 G-code 耗材顺序规划，`src/libslic3r/GCode/ToolOrdering.cpp`

## 2. 现象与复现

- 用户现象：导入工程、调整耗材或支撑配置后执行切片，程序在后台规划每层耗材顺序时退出。
- 异常类型：`EXCEPTION_ACCESS_VIOLATION_READ`。
- 崩溃平台统计：274 条崩溃记录，时间范围为 2026-08-05 至 2026-09-19。
- 详细样本口径：本地收集目录包含 25 个样本文件夹、25 份 dump、25 份 `stack.txt` 和 25 份日志压缩包；汇总文件中其余 249 条记录没有可用调用栈，不能替代详细样本作进一步分类。
- 平台：25 份样本均来自 Windows x64，覆盖 Windows 10 和 Windows 11；1 份日志缺少明确系统版本。
- 调用栈一致性：25/25 份有效调用栈均落在 `ToolOrdering::reorder_extruders_for_minimum_flush_volume()` 的精确动态规划循环，前 9 层调用路径一致：

  ```text
  ToolOrdering::reorder_extruders_for_minimum_flush_volume::<lambda>
  → tbb::parallel_for
  → TBB worker thread
  ```

- 寄存器特征：25/25 份样本的崩溃帧均出现 `rcx=0xffffffff`，且崩溃地址均对应矩阵行首地址前 4 字节，符合使用 `UINT_MAX`（无符号形式的 `-1`）作为 `float` 向量下标的表现。
- 日志侧特征：23/25 份日志记录了切片动作，17/25 包含 3MF 导入，8/25 会话最多只有 1 个耗材，说明该问题不是多耗材数量过多或多喷嘴机型的专属问题。
- 预期结果：层耗材编号异常时不访问冲刷矩阵范围之外的数据；合法工程的耗材顺序和冲刷量计算保持不变。

## 3. 根因分析

- 直接原因：最小冲刷量排序使用每层的零基耗材编号访问 `wipe_volumes[old_extruder][new_extruder]`，但普通耗材路径没有在访问前检查编号是否小于当前耗材数量。非法编号 `UINT_MAX` 因此读取到矩阵行首地址之前并触发访问冲突。
- 状态形成过程：
  1. `ToolOrdering` 收集每层所需的 1-based 耗材编号，其中 `0` 还可表示自动选择或“不关心耗材”的占位状态。
  2. 重新排序后，耗材编号通过自减转换成 0-based。若异常的 `0` 未被前序逻辑消除，Release 构建中的 `assert(extruder_id > 0)`不能阻止其下溢为 `UINT_MAX`。
  3. `reorder_extruders_for_minimum_flush_volume()` 原本拥有矩阵索引规范化逻辑，但性能优化后只在 `m_has_mixed_filaments` 为 true 时执行。
  4. 普通耗材工程中的非法编号未经校验进入精确 DP、LKH 或跨层排序，并被用作冲刷矩阵和结果数组下标。
- 历史关系：提交 `80a9ca5f`（#16663）曾在矩阵访问前无条件规范化每层耗材编号；提交 `dbb61d172` 为优化普通路径性能，将该处理限制到混色耗材条件内。7.2.1 同时包含这两个提交，因此普通耗材的非法编号保护被缩小。
- 与多喷嘴矩阵问题的关系：当前分支已通过 #17658 使用明确耗材数量提取多喷嘴矩阵，解决的是矩阵维度解释错误；本次崩溃是矩阵维度合法时，单个层耗材编号仍可能超出范围，属于独立的索引边界问题。
- 上游入口：自动支撑占位值、旧 3MF 残留耗材编号、删除耗材或切换机型后未同步的对象配置均可能形成非法编号。其中一份日志确认出现过工程耗材数量小于模型引用编号的状态；现有数据不足以证明 25 份样本全部来自同一入口。

### 业务场景（大白话）

用户正在导入工程、调整耗材或支撑设置，然后点击切片。程序后台会整理每一层要使用的耗材，并查冲刷表计算怎样换色更省料。某一层混入了自动选择占位值或已经失效的旧耗材编号，这个编号在转换时变成一个极大的数字。普通耗材路径没有检查它是否仍在冲刷表范围内，随后把它当成表格行列读取，用户最终看到切片进行到耗材排序阶段时软件突然退出。模型导入、机型切换和自动支撑是可能的放大条件，TBB 后台线程只是执行了这段排序逻辑，不是根因。

## 4. 修复方案

- 修改位置：`ToolOrdering::reorder_extruders_for_minimum_flush_volume()` 中构建冲刷矩阵之后、执行任意矩阵索引之前的层耗材规范化循环。
- 混色耗材：保留现有 `resolve_matrix_extruder_1based()` 解析逻辑，不改变虚拟耗材到物理耗材的映射。
- 普通耗材：逐个检查 `lt.extruders`；当编号大于或等于 `number_of_extruders` 时回退到零基的 0 号工具，即用户侧第 1 个耗材。
- 规范化后继续使用现有的保序去重逻辑，避免非法编号回退后产生重复工具，同时不破坏首层自定义打印顺序。
- 修复边界：本次采用发版前单点止血方案，不修改支撑耗材收集、首层顺序、编号转换、多喷嘴矩阵和混色解析流程。

## 5. 影响范围与风险

- 正向影响：阻断普通耗材工程中 `UINT_MAX`、旧工程残留编号及其他超范围编号访问冲刷矩阵的路径；同一入口同时保护精确 DP、LKH 和跨层排序中的后续下标访问。
- 正常行为：合法编号不发生任何变化，模型几何、切片参数、正常耗材顺序、冲刷体积、首层自定义顺序、多喷嘴矩阵及混色耗材逻辑保持原样。
- 性能影响：低。现有代码本来就逐层遍历耗材列表并去重，普通路径仅为每个实际使用的耗材编号增加一次整数范围比较。
- 异常工程行为：非法编号无法还原用户原本意图时统一回退到第 1 个耗材，可能改变异常对象的工具选择，但优于继续使用不存在的工具并崩溃，且与 #16663 的回退策略一致。
- 剩余风险：本次没有消除上游产生占位值或陈旧编号的所有入口；这些状态在进入最小冲刷量排序后会被安全规范化。后续可结合新增日志和崩溃趋势单独治理上游数据同步问题。
- 回退方式：移除普通耗材分支中的范围检查即可，不涉及配置格式或数据迁移。

## 6. 回归建议

- 使用代表性崩溃工程执行切片，确认不再在 `reorder_extruders_for_minimum_flush_volume()` 中访问冲突。
- 单耗材工程启用自动支撑，支撑主体和界面均使用自动选择，确认切片成功并使用有效工具。
- 导入包含超出当前耗材数量编号的旧 3MF，或删除中间/末尾耗材后重新切片，确认不崩溃且非法编号回退到第 1 个耗材。
- 在多耗材正常工程中对比修复前后的首层顺序、层间换色顺序和冲刷体积，确认合法路径结果一致。
- 设置 `first_layer_print_sequence` 和 `other_layers_print_sequence`，确认自定义顺序仍然生效。
- 分别验证混色虚拟耗材和多喷嘴机型，确认原有解析及矩阵块选择没有变化。
- 覆盖耗材数量大于精确 DP 阈值的工程，确认 LKH 路径只接收合法矩阵下标。
