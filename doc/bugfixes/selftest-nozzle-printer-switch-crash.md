## 2. 问题现象

- 用户反馈：导入 3MF，切片并等待一段时间，返回准备界面，将第四个喷嘴切换到 `0.8-标准` 时直接崩溃；后续带诊断日志复现时，切换机型也发生崩溃。
- 实际结果：Visual Studio 在 `std::map` 查找路径报告读取访问冲突，截图显示 `_Keyval` 为 `0x1F8`；调用栈经过 `OptionsGroup::get_field()`、`OG_CustomCtrl::CtrlLine::render()` 和 `OnPaint()`。
- 期望结果：切换后按当前机型和喷嘴组合更新参数界面，旧界面停止响应事件，程序正常运行。

这里的“旧控件”是切换前负责显示悬垂参数的界面对象；“新控件”是根据切换后的喷嘴布局重新创建的界面对象。用户看到的仍是同一个参数区域，但程序内部对象已经替换。

## 4. 根因分析

### 触发条件与代码链路

喷嘴布局变化时，`ConfigOptionsGroup::refresh_overhang_layout()` 重建悬垂分组。切换喷嘴经 `apply_nozzle_variant_change()`，切换机型经 `Tab::load_current_preset()`，均可进入以下公共链路：

`update_process_extruder_switch()` → `reload_config()` → 布局重建和参数回填 → `update_line_height_for_field()` → `recalculate_and_refresh()` → `Update()` → `OnPaint()` → `CtrlLine::render()` → `get_field()`。

### 问题原因

1. `CtrlLine::og_line` 保存的是参数行 `Line` 的引用。
2. 悬垂布局重建清空并重新生成 `m_lines`，旧控件的参数行引用随之失效。
3. 旧控件虽被 `on_destroyed()` 标记为 `m_is_valid=false`，但窗口仍可能收到绘制事件。
4. 原 `OnPaint()` 只判断参数组的 `custom_ctrl` 是否非空。新控件创建后，该指针非空，旧控件也会通过检查。
5. 旧控件继续读取失效行的 `opt_id`，在字段查找时发生读取访问冲突。

通用清理流程原先还会先清理部分子窗口，再停用绘制控件；鼠标移动、点击等入口的有效性检查也不统一。因此修复需要覆盖生命周期和事件入口，不能只在 `get_field()` 返回值处判空。

## 5. 修复方案

修复原则：**先停用旧控件并解绑，再释放参数数据；旧控件后续收到事件时直接停止业务处理。**

| 文件 | 修改点 |
| --- | --- |
| `src/slic3r/GUI/OptionsGroup.cpp` | 将 `on_destroyed()` 提前到 `clear()` 开始，确保解绑时字段和参数行仍有效，然后再清理子窗口及字段。 |
| `src/slic3r/GUI/OG_CustomCtrl.hpp` | 增加统一的 `is_active()` 判断，依次检查自身有效、参数组非空、当前控件身份匹配。 |
| `src/slic3r/GUI/OG_CustomCtrl.cpp` | `on_destroyed()` 支持重复调用；先标记失效，再解除字段窗口绑定到 `CtrlLine` 的进入/离开事件，最后将旧控件的 `opt_group` 置空。 |
| `src/slic3r/GUI/OG_CustomCtrl.cpp` | 绘制、鼠标移动/点击/离开、提示回调及相关显隐、行高、重排和缩放入口使用统一有效性检查。 |
| `src/slic3r/GUI/OG_CustomCtrl.cpp` | `OnPaint()` 先构造 `wxPaintDC` 完成绘制事件的正常处理，再对无效控件返回；移除本次临时诊断日志。 |

保留 `CtrlLine` 对象直到旧窗口销毁，避免解绑和回调过程中提前释放回调接收对象。窗口继续采用原有销毁流程，不强制立即删除。

本次修复集中在通用控件层，悬垂布局重建通过原有 `clear()` 调用获得保护。未修改喷嘴参数值、切片计算或悬垂分组规则。
